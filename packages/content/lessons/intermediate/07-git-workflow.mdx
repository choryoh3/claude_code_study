## ゴール

- Claude Code に commit と PR を作らせる依頼を、確認ポイント付きで出せる
- 差分の確認と権限の絞り込みで、意図しない操作を防げる
- `/rewind`（チェックポイント）と git の役割の違いを説明できる

## 前提

- git の基本（`add`、`commit`、`branch`）を知っている
- 練習用の git リポジトリがある。PR の手順には GitHub CLI（`gh`）のログインも必要

## 解説

### 依頼の仕方

公式は、PR は「create a pr for my changes」のように直接頼むか、段階を踏んで頼めると説明しています。段階を踏むほうが確認しやすくなります。

```text
今の変更を要約して
```

```text
コミットして。メッセージは Conventional Commits 形式（feat: や fix: で始める）で
```

```text
create a pr
```

```text
PR の説明に、変更のリスクと確認してほしい点を足して
```

コミットメッセージの規約があるなら CLAUDE.md に書いておくと毎回伝えずに済みます。このリポジトリも、CLAUDE.md で Conventional Commits を求めています。Claude Code 自身がコミットや PR に付ける定型文と衝突するときは、設定の `includeGitInstructions` と `attribution` で調整できます。

### 確認すべき点

1. 差分：コミット前に `git diff` や `git diff --staged` を自分で見る。PR は作る前に、Claude にリスクを列挙させる
2. 権限：git コマンドは Bash ツールとして実行されるので、権限モードや許可ルールの設定によっては確認プロンプトが出ます。プロンプトでは実行されるコマンドを読んでから許可する。自動化するなら、必要なコマンドだけ許可する
3. push や PR 作成：外部に影響する操作です。このリポジトリでは「GitHub への push は事前確認が必要」と CLAUDE.md で決めています
4. 範囲：変更をステージする前に、関係ないファイルが混ざっていないか見る

### チェックポイント（/rewind）と git の違い

| | チェックポイント（`/rewind`） | git |
| --- | --- | --- |
| 単位 | 会話のプロンプトごと | 自分が作る commit |
| 保存範囲 | Claude のファイル編集ツールによる変更 | 作業ツリー全体（commit したもの） |
| 目的 | セッション内の素早い取り消し | 永続的な履歴・共同作業 |
| 開き方 | `/rewind`、または入力欄が空のとき `Esc` を 2 回 | `git log`、`git revert` など |

制限も公式に記載があります。Bash コマンドによるファイル変更、サブエージェントの多くの編集、Claude Code の外での手動変更は、巻き戻せません。復元の選択肢は、コードと会話の両方、会話だけ、コードだけです。結論として、節目では git で commit し、`/rewind` は試行錯誤の取り消し用と考えます。

## ハンズオン

練習用の git リポジトリで行います。push はしません。

1. 作業用ブランチを作り、Claude を起動します。

   ```bash
   git switch -c practice/git-workflow
   claude
   ```

2. 小さな変更を頼みます。

   ```text
   README.md の先頭に、このリポジトリの目的を1行で追記して
   ```

3. 変更をシェルで確認します（別のターミナルで実行）。

   ```bash
   git diff
   ```

   期待される結果：追記した行だけが差分に出ます。

4. コミットを頼みます。

   ```text
   差分を確認して、Conventional Commits 形式でコミットして
   ```

   期待される結果：Claude が `git diff` などを実行し、権限の確認プロンプトを出すことがあります。内容を読んで許可すると、コミットが作られます。`git log --oneline -1` で確認します。

5. `/rewind` を試します。もう 1 つ変更を頼み、`/rewind` で直前のプロンプトを選び、「Restore code」を選びます。

   期待される結果：Claude が加えたファイル編集だけが元に戻ります。`git status` で確認します。

6. 非対話でのコミット文生成（任意）。

   ```bash
   git add -A
   claude -p "ステージされた変更を見て、適切なコミットを作って" --allowedTools "Bash(git diff *),Bash(git log *),Bash(git status *),Bash(git commit *)"
   ```

   期待される結果：許可した 4 種類のコマンドだけで、コミットが作られます。

## よくある失敗

- **`git add -A` で無関係なファイルまで commit する**
  原因：差分を見ずに任せた。対処：コミット前に `git status` と `git diff --staged` を読み、不要な物は `git restore --staged` で外す。`.env` のような秘密のファイルは、`.gitignore` に入っているか先に確認する。
- **`/rewind` で Bash の変更も戻ると思う**
  原因：チェックポイントはファイル編集ツールの変更だけを追う。対処：削除や移動を伴う作業の前に commit しておく。
- **広すぎる権限を許可する**
  原因：毎回の確認が面倒で、`Bash` 全体を許可した。対処：`Bash(git diff *)` のように、コマンド単位で許可する。
- **main に直接コミットする**
  原因：ブランチを切らずに始めた。対処：先に `git switch -c` で作業ブランチを切る。CLAUDE.md に「main に直接コミットしない」と書くと伝えやすいが、強制力はない。
- **PR を作ってから中身を読む**
  原因：自動で作られた説明を信じた。対処：作成後に PR 画面で差分と説明を読み、リスクを Claude に補足させる。
