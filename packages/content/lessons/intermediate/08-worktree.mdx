## ゴール

- git worktree の考え方を説明できる
- `claude --worktree` で、並列セッションを互いに干渉しないように起動できる
- 後片付けと、worktree 特有の落とし穴（依存・`.env`・共有されるもの）を把握する

## 前提

- git のブランチとコミットを理解している
- リポジトリに少なくとも 1 つコミットがある（worktree は既存のコミットから作られる）
- 前のレッスン（gitワークフロー）の流れを知っている

## 解説

### git worktree とは

git worktree は、同じリポジトリから「別のブランチを別のフォルダに同時にチェックアウトする」仕組みです。履歴とリモートは共有しつつ、ファイルとブランチは独立します。クローンを増やすより軽く、ブランチの切り替え（stash 不要）も要りません。

Claude Code で 2 つのセッションを同じフォルダで動かすと、同じファイルを同時に編集して衝突します。worktree ごとにセッションを分ければ、機能開発と不具合修正を並行できます。

### Claude Code の公式な方法

```bash
claude --worktree feature-auth
```

`-w` でも同じです。既定の動作は次のとおりです。

- 作成場所：リポジトリ直下の `.claude/worktrees/<name>/`
- ブランチ：`worktree-<name>`（新規）
- 名前を省略すると、`bright-running-fox` のような名前が自動で付く
- 別のターミナルで違う名前で実行すれば、2 本目の独立セッションになる
- 公式は、`.claude/worktrees/` を `.gitignore` に追加することを勧めています
- 新しい worktree は、既定ではリモートの既定ブランチ（通常は `main`）から作られる。現在の作業から分岐したい場合は、設定の `worktree.baseRef` を `"head"` にする

セッション中に「worktree で作業して」と頼むこともできます。サブエージェントを worktree で動かすこともできます（サブエージェントの詳細は別レッスン）。

### 手動で作る方法

特定の既存ブランチを使いたい、リポジトリの外に置きたいときは git を直接使います。

```bash
git worktree add ../project-feature-a -b feature-a
cd ../project-feature-a
claude
```

このリポジトリには `worktree-flow` スキルがあり、`git worktree add .claude/worktrees/<name> -b feat/<name>` で作成し、worktree 内で担当範囲だけを編集し、マージ後に `git worktree remove` と `git branch -d` で片付ける手順を定めています。

### 環境の用意

worktree は新しいチェックアウトです。依存（例：`pnpm install`）は worktree 内で実行します。`.env` のような gitignore 済みのファイルは、プロジェクト直下の `.worktreeinclude`（`.gitignore` と同じ書式）に書くと、Claude Code が作る worktree にコピーされます。手動の `git worktree add` には効きません。

### 共有されるもの

- 共有：`.git` ディレクトリ、auto memory、project スコープのプラグイン、権限の「今後確認しない」の承認（保存先がメインのチェックアウトの場合）
- 独立：作業ツリーのファイル、ブランチ、gitignore された `CLAUDE.local.md`

## ハンズオン

練習用の git リポジトリ（コミットあり）で行います。

1. `.gitignore` に追加します。

   ```bash
   echo ".claude/worktrees/" >> .gitignore
   ```

   Windows(PowerShell) の場合は次のとおりです。

   ```powershell
   Add-Content .gitignore ".claude/worktrees/"
   ```

2. 1 つ目のターミナルで worktree セッションを起動します。

   ```bash
   claude --worktree practice-a
   ```

   期待される結果：`.claude/worktrees/practice-a/` ができ、そこが作業ディレクトリのセッションが始まります。

3. 小さな変更を頼みます。

   ```text
   practice-a.txt というファイルを作り、1行だけ書いて
   ```

4. 2 つ目のターミナルで、同じリポジトリから別の名前で起動します。

   ```bash
   claude --worktree practice-b
   ```

   期待される結果：`practice-a.txt` は、こちらのセッションには存在しません。

5. 3 つ目のターミナルで、worktree の一覧とブランチを確認します。

   ```bash
   git worktree list
   git branch --list "worktree-*"
   ```

   期待される結果：メインと 2 つの worktree、`worktree-practice-a` と `worktree-practice-b` が表示されます。

6. 各セッションを終了します。作業が残っていると、worktree を残すか削除するかを聞かれます。練習なので削除を選びます。手動で片付ける場合は次のとおりです。

   ```bash
   git worktree remove .claude/worktrees/practice-a
   ```

## よくある失敗

- **コミットが 1 つもないリポジトリで失敗する**
  原因：worktree は既存のコミットから作る。対処：先に最初のコミットを作る。公式にも、この場合はエラーになると記載がある。
- **worktree で `pnpm verify` が通らない（依存がない）**
  原因：node_modules は worktree に引き継がれない。対処：worktree 内で `pnpm install` を実行する。
- **`.env` が無くて動かない**
  原因：gitignore されたファイルはコピーされない。対処：`.worktreeinclude` に書く。秘密のファイルなので、`.gitignore` にも入っていることを確認し、コミットしない。
- **フォルダだけ削除して、git に登録が残る**
  原因：`rm -rf` やエクスプローラーで消した。対処：`git worktree remove` を使う。残ってしまったら `git worktree list` で状況を確認する。
- **未コミットの作業ごと worktree を削除する**
  原因：終了時の削除プロンプトで、作業が残っているのに削除を選んだ。対処：公式の説明どおり、削除するとディレクトリとブランチが、作業ごと消える。残したい作業は先にコミットする。
