## ゴール

- subagent の並列実行と git worktree の違い・使い分けを説明できる
- 担当範囲（パッケージ境界）を決めて、衝突しにくい分担を設計できる
- worktree で 2 つの作業を同時に進め、マージまでできる

## 前提

- 基礎レッスンと中級を終えている（subagent の基本的な使い方、CLAUDE.md、hooks の概念を知っている）
- Git の基本操作（ブランチ、マージ）ができる
- コミットが 1 つ以上あるリポジトリを用意している（worktree はコミットから作られるため）

## 解説

### 並列化の手段は 2 種類ある

公式ドキュメントは、並列で動かす方法をいくつか紹介しています。このレッスンで使うのは次の 2 つです。

| 手段 | 何を分けるか | 向いている用途 |
| --- | --- | --- |
| subagent | コンテキスト（会話の記憶領域） | 調査や検証など、結果の要約だけが欲しい作業 |
| git worktree | ファイル（作業ディレクトリとブランチ） | 同時に別々のファイルを編集する実装 |

git worktree は、同じリポジトリを共有しつつ、別のディレクトリ・別のブランチにチェックアウトする Git の機能です。公式は、worktree が「ファイル編集を分離する」もの、subagent が「1 つのセッション内で作業を分ける」ものだと整理しています。

### subagent の並列実行

公式の例では、「認証・DB・API の各モジュールを、別々の subagent で並列に調べて」のように頼むと、Claude が複数の subagent を同時に動かします。各 subagent は独立したコンテキストで動き、結果の要約が元の会話に戻ります。

- 返ってきた結果はすべてメインのコンテキストを消費する。並列に増やすほど、戻ってくる要約も増える
- 同時に動かせる数はデフォルトで 20。環境変数 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` で変えられる

### worktree で編集を分離する

```bash
claude --worktree feature-auth
```

公式の仕様では、デフォルトで `.claude/worktrees/<name>/` に、`worktree-<name>` という新しいブランチで作られます。別のターミナルで別の名前を指定すれば、2 つ目の独立したセッションになります。注意点は次のとおりです。

- worktree は新規チェックアウトなので、依存関係のインストールは worktree 側で行う
- `.env` のような gitignore 済みファイルは持ち込まれない。必要なら `.worktreeinclude` に書く
- 起点は、デフォルトでリモートのデフォルトブランチ。現在の作業状態から始めたいときは、設定 `worktree.baseRef` を `"head"` にする
- `.claude/worktrees/` を `.gitignore` に入れておくと、メインの作業ツリーに未追跡ファイルとして出ない

subagent を worktree で動かすには、「agent に worktree を使わせて」と頼むか、カスタム subagent の frontmatter に `isolation: worktree` を書きます。変更がなければ一時 worktree は自動で削除されます。

hooks を使っている場合の注意が 1 つあります。公式によると、Claude が worktree に入った後も `${CLAUDE_PROJECT_DIR}` は元のプロジェクトルートを指し続け、worktree のパスは hook の入力 JSON の `cwd` で渡されます。

### 担当範囲で衝突を避ける（設計指針）

ここからは公式の仕様ではなく、一般的な設計指針です。このリポジトリの `worktree-flow` skill もこの考え方を採用しています。

1. パッケージ境界で担当を分ける（例: `apps/api` と `apps/web` と `packages/content`）
2. 共有の契約（このリポジトリでは `packages/schemas`）は、並列に入る前に確定させる
3. 担当外のファイルが必要になったら、作業を止めて相談する。黙って触らない
4. 各担当は worktree 内で `pnpm verify` を通してから戻す

並列化の向き不向きは次のとおりです。

- 向く: 独立したパッケージの実装、互いに依存しない修正、書き込みのない調査
- 向かない: 同じファイルを触る作業、前の結果が次の入力になる作業、共有スキーマ自体の設計

### マージの進め方

並列化の本当のコストはマージです。小さい単位で、1 本ずつ検証してから統合します。このリポジトリの `worktree-flow` は「作成 → 作業 → 検証 → PR → 独立レビュー → マージ後に削除」の順です。

## ハンズオン

コミットが 1 つ以上ある、練習用の Git リポジトリで行います。

1. ターミナル A で、1 つ目の worktree 付きセッションを始めます。初回はそのディレクトリで一度 `claude` を起動して、信頼ダイアログを承認しておきます（公式の仕様）。

   ```bash
   claude --worktree docs-a
   ```

   期待される結果：`.claude/worktrees/docs-a/` が作られ、Claude がその中で起動します。

2. ターミナル B で、別の名前でもう 1 つ起動します。

   ```bash
   claude --worktree docs-b
   ```

3. A では `docs/a.md` を、B では `docs/b.md` を作るよう、それぞれ頼みます（別のファイルなので衝突しません）。

   ```text
   docs/a.md を作り、1行の自己紹介を書いて、コミットして
   ```

4. 3 つ目のターミナルで、メインのチェックアウトから状況を確認します。

   ```bash
   git worktree list
   git branch --list "worktree-*"
   ```

   期待される結果：メインと 2 つの worktree が表示され、`worktree-docs-a` と `worktree-docs-b` のブランチがあります。

5. メインのチェックアウトで、1 本ずつ統合します。

   ```bash
   git merge worktree-docs-a
   git merge worktree-docs-b
   ```

   期待される結果：別ファイルなので、どちらも衝突なくマージされます。

6. 各ターミナルで `/exit` します。変更をマージ済みでも、コミットがあるとキープか削除かを聞かれます。不要なら削除を選びます。

7. 余裕があれば、メインのセッションで subagent の並列調査も試します。

   ```text
   docs ディレクトリの各ファイルを、別々の subagent で並列に要約して
   ```

## よくある失敗

- **worktree に最新の作業が入っていない**
  原因：起点がリモートのデフォルトブランチで、未 push のコミットを含まない。対処：先に push する、または `worktree.baseRef` を `"head"` にする。
- **worktree で依存関係がなくてテストが動かない**
  原因：worktree は新規チェックアウトで、`node_modules` も `.env` もない。対処：worktree 内でインストールを実行し、`.env` が要るなら `.worktreeinclude` に書く。
- **2 つのセッションが同じファイルを編集してマージが衝突する**
  原因：担当範囲が重なっている。対処：パッケージ境界で分け直す。共有物は先に確定させ、直列で進める。
- **subagent を増やしすぎて、メインのコンテキストが埋まる**
  原因：並列にした全 subagent の要約がメインに戻る。対処：用途を絞り、結果は短く要約するよう指示する。
- **worktree を放置して溜まる**
  原因：手動で `git worktree add` したものは自動削除の対象外。対処：マージ後に `git worktree remove` で削除し、`git worktree list` で定期的に確認する。
