## ゴール

- チームで共有してよい設定と、個人に留める設定を区別できる
- 設定のスコープと優先順位から、「どこに書けば誰に効くか」を判断できる
- 権限・フック・MCP・CLAUDE.mdで標準化し、必要なら管理設定で強制する設計を説明できる

## 前提

- 基礎レッスンの権限モードとCLAUDE.mdを終えていること
- 上級の「ハーネスエンジニアリング」（`/learn/advanced/harness-engineering`）で、hooksによる強制の考え方に触れていると理解しやすい（必須ではありません）
- Gitでリポジトリを共有する経験があること

**ガバナンス** は、ここでは「誰が何をできるかを、ルールと仕組みで決めて保つこと」を指します。

## 解説

### 共有してよいもの、いけないもの

プロジェクトの設定をリポジトリに入れると、clone した全員が同じ環境で始められます。

| 置き場所                                               | 共有   | 内容                                                                                                       |
| :----------------------------------------------------- | :----- | :--------------------------------------------------------------------------------------------------------- |
| `CLAUDE.md`                                            | する   | 毎回読む短い方針（公式は1ファイル200行未満を目安に）                                                       |
| `.claude/settings.json`                                | する   | チームの権限、フック、プラグイン、必要な環境変数                                                           |
| `.claude/rules/`、`.claude/skills/`、`.claude/agents/` | する   | パス別規約、手順、専門エージェント                                                                         |
| `.mcp.json`                                            | する   | チームで使うMCPサーバー                                                                                    |
| `.claude/settings.local.json`                          | しない | 個人の上書き。Claude Codeが作る場合は、自動でgit管理外になる。手で作ったなら `.gitignore` に自分で追加する |
| `CLAUDE.local.md`                                      | しない | 個人のプロジェクト固有メモ。`.gitignore` に追加する                                                        |

このリポジトリでも `.claude/settings.local.json` は `.gitignore` に入っています。

### スコープと優先順位

同じキーが複数の場所にあると、設定された最も高いレベルの値が使われます。高い順に次のとおりです。

1. 管理設定（組織が配布。上書きできない）
2. コマンドライン（`--settings`。そのセッションだけ）
3. プロジェクトローカル（`.claude/settings.local.json`）
4. 共有プロジェクト（`.claude/settings.json`）
5. ユーザー（`~/.claude/settings.json`）

`permissions.allow` のようなリストは、上書きではなく **結合** されます。つまり、チームが許可した項目に、個人が自分の分を足せます。逆に言うと、**チームの許可を個人が消すことはできません**。そして、deny（拒否）は allow より先に評価され、allow で例外を作れません。守らせたい規則は deny に置きます。

### 権限の標準化

共有設定に、次を入れるのが基本形です。

- `allow`: 毎回確認されると手が止まる、安全なコマンド（`pnpm *`、読み取り系のgitなど）
- `ask`: 確認したい操作（`git push*` など）
- `deny`: 絶対に許さない操作（`.env` の読み取り、`rm -rf*`、force pushなど）

このリポジトリの `.claude/settings.json` は、この3段構成です。`Read(./.env)` のような `.env` の読み取りを deny にし、`git push*` は ask にしています。

### フックでガードレールを作る

CLAUDE.mdの指示は、Claudeへの「お願い」で、強制ではありません。確実に止めたいなら、`PreToolUse` フックを使います。終了コード2で呼び出しをブロックでき、標準エラー出力の内容がClaudeに返ります。

このリポジトリの `.claude/hooks/guard-bash.mjs` は、`rm -rf`、force push、`git add --force`、`.env` のコミットをこの方法でブロックします。

注意点が2つあります。

- フックは、ユーザーが定義したシェルコマンドを自動実行します。つまり **コードです**。共有設定に入れたフックの変更は、アプリのコードと同じようにレビューします（GitHubなら、CODEOWNERSで `.claude/` の変更に担当者のレビューを必須にする手があります）
- 公式は、確実な許可・拒否のルールには、フックではなく権限システムを使うよう勧めています。フックは補強として使います

### MCPの承認とセキュリティ

- 対話セッションでは、`.mcp.json` のサーバーは使用前に承認を求められます。ただし `claude -p`（CIなど）では、尋ねずに読み込まれます。外したいサーバーは `disabledMcpjsonServers` に入れます
- リポジトリ自身は、自分のサーバーを承認できません。コミットした `.claude/settings.json` の `enableAllProjectMcpServers` などは、信頼していないフォルダでは無視されます
- 認証情報は、URLに直書きせず、`.mcp.json` の環境変数展開（`${VAR}` 形式）を使います
- 外部コンテンツを取得するサーバーは、プロンプトインジェクションの危険があるため、信頼できるものだけにします

このリポジトリの `.mcp.json` にはPlaywrightとSupabaseが入っています。CLAUDE.mdでは、MCPの追加を「事前確認が必要な操作」にしています。

### 組織での配布と強制

チームの共有設定（コミットするファイル）は、慣習とレビューで守る層です。**強制** したいなら、管理設定を使います。公式が説明する配布方法は3つです。

| 方法                   | 内容                                                                                                                                                             |
| :--------------------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| サーバー管理設定       | claude.aiの管理コンソールで配布する。端末への作業が要らない                                                                                                      |
| MDM/OSレベルのポリシー | macOSの構成プロファイルやWindowsのレジストリ。Jamf、Intuneなどで配布する                                                                                         |
| ファイル               | `managed-settings.json` を、macOSは `/Library/Application Support/ClaudeCode/`、Linux/WSLは `/etc/claude-code/`、Windowsは `C:\Program Files\ClaudeCode\` に置く |

管理設定は、ユーザー・プロジェクト・コマンドラインのどの設定でも上書きできません（ごく一部のセキュリティ関連キーを除く）。代表的な制御キーは次のとおりです。

- `allowManagedPermissionRulesOnly`: 権限ルールを管理設定だけにする
- `allowManagedHooksOnly`: 実行できるフックを制限する
- `allowManagedMcpServersOnly`: MCPの許可リストを管理設定のものだけにする

組織共通のCLAUDE.mdも、管理ポリシーの場所（Linux/WSLなら `/etc/claude-code/CLAUDE.md`）に置けます。どのキーを強制するか、配布方法の優先順位、グループ別配布の可否などは、公式の管理設定のページで確認してください。

### オンボーディング

新メンバーには、clone後に `claude` を起動し、信頼ダイアログを確認し、`/status`（設定の読み込み元）、`/permissions`、`/hooks`、`/mcp` で、いまの設定を見る手順を渡します。CLAUDE.mdが空なら `/init` で下書きを作れます。

## ハンズオン

このリポジトリ、または自分のプロジェクトで、共有の状態を点検します。

1. 共有されているファイルを確認します。

   ```bash
   git ls-files .claude .mcp.json CLAUDE.md
   ```

   期待される結果: `.claude/settings.json`、`.claude/hooks/`、`.claude/rules/`、`.claude/skills/`、`.mcp.json`、`CLAUDE.md` などが並びます。`.claude/settings.local.json` は含まれません。

2. 個人設定がgit管理外であることを確認します。

   ```bash
   git check-ignore -v .claude/settings.local.json
   ```

   期待される結果: `.gitignore` のどの行で除外されているかが表示されます。何も出なければ、除外されていません。`.gitignore` に追加してください。

3. Claude Codeを起動し、設定の読み込み元を見ます。

   ```text
   /status
   /permissions
   /hooks
   ```

   期待される結果: `/status` の設定ソースに、ユーザー・プロジェクトなどが並びます。管理設定が適用されている場合は `Enterprise managed settings` が出ます。`/permissions` で deny ルール、`/hooks` で `PreToolUse` などのフックを確認できます。

4. 権限のdenyを試します。ダミーの `.env`（`DUMMY=1` だけ）を作り、Claudeに依頼します。

   ```text
   .env の中身を読んで教えて
   ```

   期待される結果: `Read(./.env)` の deny ルールにより、ファイル読み取りツールでの読み取りが拒否されます。シェル経由など別の経路まで防げるかは、ルールの書き方と構成で変わるため、`.env` は権限ルールだけに頼らず、コミットもフックで防ぐ（このリポジトリの方式）のが安全です。

5. フックのブロックを試します。使い捨てのリポジトリで、Claudeに依頼します。

   ```text
   git add --force dummy.txt を実行して
   ```

   期待される結果: 設定の `allow` に `git add*` があっても、フックが終了コード2でブロックし、`[guard-bash] ブロック: git add --force は禁止です` の理由がClaudeに返ります。フックは許可ルールとは別に働きます。

6. （任意、検証用の別環境で）管理設定を試します。次のファイルを、前述のOS別の場所に置き、Claude Codeを再起動して `/status` を見ます。

   ```json
   {
     "permissions": {
       "deny": ["Read(./.env)", "Read(./secrets/**)"],
       "disableBypassPermissionsMode": "disable"
     },
     "allowManagedPermissionRulesOnly": true
   }
   ```

   期待される結果: 設定ソースに `Enterprise managed settings (file)` が出ます。このファイルは、自分のユーザー・プロジェクトの許可ルールを無視させるため、普段使いのPCには置かないでください。

## よくある失敗

- **個人用の設定をコミットしてしまう**
  - 原因: `.claude/settings.local.json` を手で作り、`.gitignore` に追加していない
  - 対処: `git check-ignore -v` で確認。個人のAPIキーや設定は、共有ファイルに入れない
- **「CLAUDE.mdに書いたのに守られない」**
  - 原因: CLAUDE.mdは文脈として読まれるだけで、強制力がない
  - 対処: 必ず守らせたいことは、denyルールか `PreToolUse` フックにする。管理設定で全員に強制もできる
- **共有設定の変更をレビューしない**
  - 原因: `.claude/` を「ただの設定」と考え、フックやMCP、allowの追加が素通りする
  - 対処: フックはコード、allowは権限の拡大として扱い、PRでレビューする。CODEOWNERSで担当者を決める
- **CIでMCPやフックが意図せず動く**
  - 原因: `claude -p` は信頼ダイアログもMCPの承認も出さず、リポジトリのフックと `.mcp.json` をそのまま使う
  - 対処: CIでは `--bare` を付ける、`disabledMcpjsonServers` で外す、などで制御する（`/learn/advanced/ci-integration`）
- **管理設定が効いていない**
  - 原因: 配置場所やファイル名の誤り、複数の配布方法の併用（既定では1つだけが使われる）、JSONの文法エラー
  - 対処: `/status` で設定ソースを確認する。JSONは、コメントや末尾カンマが許されない厳密な形式
