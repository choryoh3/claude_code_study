## ゴール

- 指示を「何を・どこで・どう確認するか」の3点で組み立てられる
- 公式が勧める「調べる → 計画 → 実装」の流れを使い分けられる
- うまくいかないときに、訂正を重ねずに立て直せる

## 前提

- Claude Code を起動して、基本的なやり取りができる
- プランモード（`Shift+Tab` で切り替える、変更しない調査・計画用のモード）と `/clear` を知っている

## 解説

この回の根拠は、公式のベストプラクティス記事です。公式記事にない一般論は「一般的な指針」と明記します。

### 指示に確認手段を含める

公式が最初に挙げるのが、Claude が自分で実行できる確認手段（テスト、ビルド、スクリーンショットなど）を渡すことです。確認手段がないと、あなたが毎回の確認役になります。

| 観点     | 悪い例                     | 良い例                                                                                                     |
| -------- | -------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 確認手段 | 「メール検証関数を作って」 | 「`validateEmail` を作って。例：`user@example.com` は true、`invalid` は false。実装後にテストを実行して」 |
| 根本原因 | 「ビルドが失敗する」       | 「このエラーでビルドが失敗する。直して、ビルド成功を確認して。エラーの抑制ではなく根本原因を直して」       |

### 具体的な文脈を渡す

公式は「指示が正確なほど訂正が減る」としています。範囲・参考にする既存の実装・症状と「直った」の基準を書きます。

- 範囲を絞る：「`foo.py` のテストを足して」より「`foo.py` で、ユーザーがログアウト済みの場合のテストを書いて。モックは使わない」
- 既存パターンを示す：「カレンダーを追加して」より「ホームの既存ウィジェットの実装を見て、そのパターンに沿って作って」
- 症状を書く：「ログインのバグを直して」より「セッションのタイムアウト後にログインが失敗する。`src/auth/` のトークン更新を確認して。まず再現する失敗テストを書いてから直して」

ファイルは `@` を付けて参照できます。画像の貼り付けや URL の指定も有効です。

### 調べる → 計画 → 実装

公式の推奨は、探索・計画・実装・コミットの4段階です。プランモードで先に調べて計画させると、的外れな実装を避けられます。ただし、差分を一文で説明できる小さな変更では計画は不要です。

### 一般的な指針

以下は公式記事の直接の主張ではなく、上記を踏まえた一般的な指針です。

- 1回の指示では1つの目的に絞る
- 「やらないこと」（範囲外）も書く
- 曖昧な探索（「何を改善できる？」）は、やり直せる場面でなら有効

## ハンズオン

1. 自分のプロジェクトで Claude Code を起動し、まず曖昧な指示を試します。

   ```text
   READMEを良くして
   ```

   期待される結果：何をどう直すかが定まらず、意図とずれた提案が返りがちです。必要なら `Esc` で止めます。

2. `/clear` でリセットし、3点（対象・方針・確認手段）を入れた指示に変えます。`@` の後のファイル名は自分のプロジェクトに合わせてください。

   ```text
   @README.md を見て、セットアップ手順が実際のコマンドと合っているか確認して。
   違う箇所だけ修正して、構成や文体は変えないで。
   修正前後の差分を最後に一覧で見せて。
   ```

   期待される結果：対象が README.md に限られ、修正箇所が絞られ、差分一覧という根拠が返ってきます。

3. 次に、変更の前に調べさせます。`Shift+Tab` を押してステータス表示が plan mode になるまで切り替え、次を送ります。

   ```text
   このプロジェクトのテストの実行方法と、テストファイルの置き場所を調べて。変更はしないで。
   ```

   期待される結果：ファイルは変更されず、調べた結果の説明だけが返ります。

4. 2回訂正しても直らない状況を想定し、`/clear` してから、学んだ条件を含めた最初の指示を書き直します。

## よくある失敗

- **確認手段を渡さない**
  原因：「できたように見える」だけで完了扱いになる。対処：テスト・ビルド・スクリーンショットなど、合否が読める確認を指示に入れ、実行結果を見せてもらう。
- **ひとつのセッションに無関係な作業を詰め込む**
  原因：コンテキストが無関係な情報で埋まる。対処：作業が変わるたびに `/clear` する。
- **訂正を何度も重ねる**
  原因：失敗した試行がコンテキストに残る。対処：2回直らなければ `/clear` して、より具体的な最初の指示で始め直す。
- **範囲を決めずに「調査して」と頼む**
  原因：大量のファイルを読み、コンテキストを消費する。対処：調べる範囲を絞る。公式は、調査をサブエージェントに任せる方法も紹介しています（詳細は上級で扱う）。
- **小さな修正にまでプランモードを使う**
  原因：計画の手間のほうが大きい。対処：差分を一文で言える変更は直接頼む。
