## 1. E2E とは何か

**E2E（End-to-End）テスト**は、「入口から出口まで」を通して確認するテストです。ここでの「入口」は利用者の操作（クリック、キー入力、ページ遷移）、「出口」は画面に表示される結果です。

アプリ開発のテストは、大きく3層に分けて考えます。

## 2. なぜ必要か（効用）

ユニットテストが全部通っても、**画面が壊れていること**は珍しくありません。実際に、このプロジェクトの開発中に、**実ブラウザでの検査**（E2E と同じ方法）で見つかった不具合があります。

| 見つかった不具合                                                               | ユニットテストで見つかるか |
| ------------------------------------------------------------------------------ | -------------------------- |
| スマホの画面で、レッスンが横に 345px はみ出す                                  | ✗（見た目の問題）          |
| ページを開いた一瞬、全員に「未着手」と誤表示される（ハイドレーション前の状態） | ✗（ブラウザの挙動）        |
| 検索ボタンの読み上げ名が、見えている文字とずれている（WCAG 2.5.3 違反）        | ✗（アクセシビリティ）      |
| スマホの下部タブバーの文字が、背景が透けてコントラスト不足（WCAG 1.4.3 違反）  | ✗（実際の色の組み合わせ）  |

E2E の効用を、まとめると次のとおりです。

1. **「動くアプリ」を保証できる**: 部品ごとの正しさではなく、**組み合わせた結果**を確認する。
2. **回帰（リグレッション）を防げる**: 機能を足したり直したりして、**別の場所が壊れた**ときに、すぐ気づける。
3. **公開前の最終確認を、人の手から機械に移せる**: 「主要画面を全部開いて、ひと通り操作する」を毎回手でやるのは、遅く、見落としが出る。
4. **アクセシビリティの退化を防げる**: 配色や部品を変えたときに、基準を下回っていないかを、毎回同じ物差しで測れる。
5. **仕様の「生きたドキュメント」になる**: 「クイズは満点でバッジが出る」「検索は Ctrl+K で開く」といった期待が、実行できる形で残る。

> **限界**: E2E は遅く、壊れやすく（待ち時間のずれなど）、原因の特定も難しい。そのため、**細かい論理はユニットテストで、主要な利用シナリオだけを E2E で**確認するのが定石です（「テストピラミッド」）。このリポジトリも、その方針です。

## 4. 実行のしかた

E2E は、**本番と同じビルド**を対象にします。開発サーバー（`next dev`）では、初回アクセスごとにコンパイルが走って遅く、本番とも挙動が違うためです。

### 4-1. 事前準備（初回だけ）

```bash
# 依存を入れる（e2e は pnpm のワークスペースに含まれている）
pnpm install

# 検査用のブラウザ（Chromium）を入れる。playwright-core はブラウザを同梱しないため。
pnpm --filter @claude-study/e2e exec playwright-core install chromium
```

すでに Chromium がある場合は、導入を省いて、実行ファイルを `CHROME_EXE` で指定できます（[7. トラブルシュート](#7-落とし穴とトラブルシュート)）。

### 4-2. 本番ビルドを起動する

```bash
pnpm --filter @claude-study/web build
pnpm --filter @claude-study/web start -p 3100
```

> ⚠ **ポートに注意**: `next start` の既定ポートは **3000** ですが、E2E の既定の接続先は **3100** です。上のように `-p 3100` を付けるか、E2E 側を `BASE_URL=http://localhost:3000` で合わせてください。

起動は、別のターミナルで行い、動かしたままにします。

### 4-3. 検査を実行する

```bash
# すべて
pnpm e2e

# 1つだけ
pnpm --filter @claude-study/e2e run site
pnpm --filter @claude-study/e2e run learning
pnpm --filter @claude-study/e2e run content
pnpm e2e:a11y        # アクセシビリティだけ
```

### 環境変数

| 変数         | 意味                                                                            | 既定                        |
| ------------ | ------------------------------------------------------------------------------- | --------------------------- |
| `BASE_URL`   | 検査対象のURL                                                                   | `http://localhost:3100`     |
| `OUT_DIR`    | スクリーンショットの保存先                                                      | `<リポジトリ>/evidence/e2e` |
| `CHROME_EXE` | ブラウザの実行ファイル（未指定なら、Playwright が探した既定の Chromium を使う） | （なし）                    |

スクリーンショットは `evidence/` に保存されます。このフォルダは **git に含めません**（画像が大きくなるため）。画面を目で確認したいときに開いてください。

### 所要時間

`site` は HTTP だけなので数秒で終わります。ほかは、ブラウザで実際に操作して待つため、分単位かかります。`a11y` が最も長く、ページ数 ×（ライト/ダーク）×（デスクトップ/モバイル）の56回を、順に検査します。正確な時間は、マシンとネットワークで大きく変わるので、ここでは示しません。

## 5. 結果の読み方

### site / learning / content

1行が1つの確認項目です。

```text
PASS  クイズ: 満点で「全問正解です！」
FAIL  ホーム: 見出しがリッチテキストで組み立てられる — Claude Codeを、任せられる相棒に育てる。

45 passed, 2 failed
```

- `FAIL` が **1つでもあれば、終了コードが 1** になります（コマンドが失敗扱い）。
- `—` の後ろは、**実際に得られた値**です。期待値とのずれを見て、原因を考えます。
- `ABORTED …` は、検査の途中で**処理自体が止まった**ことを示します（要素が見つからない、サーバーが起動していない、など）。

### a11y

違反は、**ルール、場所、要素、理由**の順に表示されます。

```text
FAIL  light/mobile / — [serious] color-contrast: Elements must meet minimum color contrast ratio thresholds
        .tab[href$="roadmap"] > span
        <span>ロードマップ</span>
        → Element has insufficient color contrast of 4.39 ... Expected contrast ratio of 4.5:1
```

| 部分                         | 意味                                                                                           |
| ---------------------------- | ---------------------------------------------------------------------------------------------- |
| `light/mobile /`             | どの条件で: ライトテーマ・モバイル幅・トップページ                                             |
| `[serious]`                  | 影響度（`minor` < `moderate` < `serious` < `critical`）                                        |
| `color-contrast`             | 違反したルールの ID（[axe のルール一覧](https://dequeuniversity.com/rules/axe/) で調べられる） |
| 2行目以降（セレクタと HTML） | **どの要素か**                                                                                 |
| `→`                          | **なぜ違反か**（この例は、コントラスト比が 4.39 で、基準 4.5 に届かない）                      |

最後に、次のように集計が出ます。

```text
56 件の検査（wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa）: 違反 0 件、要確認 N 件
```

- **違反**: 機械が「基準を満たしていない」と**確定できたもの**。1件でもあれば失敗（終了コード 1）。
- **要確認（incomplete）**: 機械では**判定できなかったもの**（例: 背景が画像やグラデーションで、色が確定できない）。**失敗にはしません**が、内訳が出力されるので、**人が目で確認**してください。

> **重要**: アクセシビリティの機械検査は、問題の**一部しか**見つけられません。「違反 0 件」は、「アクセシブルである」ことの証明ではありません。キーボードだけで一通り操作する、スクリーンリーダーで読み上げを聞くなどの、**手動の確認**と併用してください。

## 6. 検査を足す・直す

### 検査を足すときの型

`learning.mjs` や `content.mjs` に、次の形で足します。

```js
// 1. ページを開く
await page.goto(`${BASE}/badges`, { waitUntil: 'domcontentloaded' });

// 2. 要素を「役割と名前」で探して操作する（CSSのクラス名に頼らない）
await page.getByRole('button', { name: 'コピー' }).first().click();

// 3. 結果を確認して、check(名前, 成否, 詳細) に記録する
check('コピー: 「コピーしました」と表示される', await page.getByText('コピーしました').isVisible());
```

- **要素の探し方の優先順位**: `getByRole`（役割と名前）→ `getByText`（見える文字）→ `data-*` 属性 →（最後の手段）CSS。見た目のためのクラス名は、ビルドのたびに変わる（CSS Modules）ので、使わない。
- **`check()` の名前は、「何が、どうなっていればよいか」を日本語で書く**。失敗したときに、それだけで原因の見当がつくように。
- **値の詳細（第3引数）を付ける**と、失敗時に実際の値が見えて、調査が速い。

### 画面に文言を足したとき

文言は辞書（`apps/web/messages/ja.json`）にあります。検査が文言（「全問正解です！」など）で要素を探している場合は、**辞書を変えたら、検査側の文言も合わせて直す**必要があります。

### 共通部品（`lib.mjs`）

| 関数               | 役割                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- |
| `createReporter()` | 結果の集計と、最後の表示・終了コードの決定                                         |
| `launchBrowser()`  | ブラウザの起動（`CHROME_EXE`、保存先フォルダの作成）                               |
| `loadQuiz()`       | レッスンのファイルから、クイズの**正解の文言**を読む（満点を取る操作に使う）       |
| `startQuiz()`      | クイズを開始する。**ハイドレーション前のクリックの取りこぼし**を、再試行で吸収する |
| `openPalette()`    | 検索パレットを開く（キーボード／タップ）。同じく、取りこぼしを再試行で吸収する     |

## 7. 落とし穴とトラブルシュート

E2E で最も多い失敗の原因は、**アプリの不具合ではなく、待ち時間のずれ**です。

### ハイドレーション前の操作が、取りこぼされる

Next.js は、まず HTML を表示し、そのあとブラウザ側で JavaScript を動かして、ボタンなどを「操作できる状態」にします（これを**ハイドレーション**と言います）。**表示された直後は、まだボタンを押しても反応しません**。

人間は気づかない程度の差ですが、自動操作は速いので、この間に押してしまい、**何も起きずに検査が失敗**します。

- 対処: `lib.mjs` の `startQuiz()` / `openPalette()` のように、**目的の状態になるまで、操作を再試行する**。
- やってはいけないこと: 固定の `waitForTimeout(3000)` を増やして、「たぶん大丈夫」にする（遅く、それでも不安定）。

### よくあるエラー

| 症状                                                         | 原因                                                  | 対処                                                                                                |
| ------------------------------------------------------------ | ----------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| `net::ERR_CONNECTION_REFUSED`                                | サーバーが起動していない／ポートが違う                | `pnpm --filter @claude-study/web start -p 3100` を起動する。または `BASE_URL` を合わせる            |
| `Could not find a production build in the '.next' directory` | `build` をしていない                                  | 先に `pnpm --filter @claude-study/web build`                                                        |
| `Executable doesn't exist at ...chrome...`                   | ブラウザが入っていない／Playwright が期待する版と違う | `playwright-core install chromium` を実行する。または、手持ちの Chromium を `CHROME_EXE` で指定する |
| `strict mode violation: locator(...) resolved to 2 elements` | 探した条件に、複数の要素が一致した                    | 条件を絞る（`.first()`、親要素の指定、`exact: true`）                                               |
| `Timeout ... waiting for ...`                                | 要素が現れない（本当に壊れている／待ち方が悪い）      | スクリーンショットを撮って、実際の画面を確認する。ハイドレーション前の操作なら、再試行にする        |
| 辞書を変えたあと、文言に関する検査だけが落ちる               | 検査が、古い文言で探している                          | 検査側の文言を、辞書に合わせて直す                                                                  |

### 失敗の原因が分からないとき

1. **スクリーンショットを撮る**: `await page.screenshot({ path: 'debug.png' })` を、失敗する直前に入れて、実際の画面を見る。
2. **状態を出力する**: `console.log(await page.locator('main').innerText())` で、画面の文字を見る。
3. **ブラウザを表示して動かす**: `launchBrowser()` の `chromium.launch({ headless: false })` に変えると、実際の動きを目で追える（確認後は戻す）。
4. **1つだけ実行する**: `pnpm --filter @claude-study/e2e run site` など、小さい単位で切り分ける。

## 8. CI について（現状と提案）

**現状、E2E は CI（GitHub Actions）では実行していません。** CI が実行するのは、`pnpm verify`（書式・lint・型・ユニットテスト・ビルド）です。E2E は、手元で、公開前や大きな変更のあとに実行します。

### 理由

- ビルドしたアプリの起動と、ブラウザの導入が必要で、実行が**分単位**かかる。
- 待ち時間のずれによる**偶発的な失敗**があり得て、必須チェックにすると、PR が不当に止まりやすい。

### 導入するなら（提案）

1. **まず「必須でない」ワークフローとして追加する**（失敗しても PR は止めない）。安定したことを確かめてから、必須にするかを決める。
2. **`site` を先に CI に入れる**（ブラウザ不要で速く、偶発的な失敗が少ない）。セキュリティヘッダーの欠落などを、PR の段階で防げる。
3. **`a11y` は、夜間・週次の定期実行**にする（時間がかかるため）。違反が出たら通知する。
4. ワークフローを足すときは、`.github/` の規約（アクションの SHA 固定、最小権限、`timeout-minutes`）に従う。詳しくは [`docs/github-setup.md`](../docs/github-setup.md) を参照。
