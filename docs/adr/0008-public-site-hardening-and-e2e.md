# 0008. 公開サイトとしての仕上げ（セキュリティヘッダー・規約・メタデータ）と、E2E・アクセシビリティ検査

- 日付: 2026-10-20
- 状態: 採用（CSP は未対応）

## 背景

フェーズ7で、アプリを不特定多数に公開できる状態に仕上げる。公開に必要なものと、品質の保ち方を決める。ログイン（GitHub OAuth）は、Supabase 側の設定は済んだが、アプリには未実装で、永続ストアも未接続。

## 決定

### セキュリティヘッダー

`next.config.ts` で全ページに付ける。

| ヘッダー                                           | 狙い                                                         |
| -------------------------------------------------- | ------------------------------------------------------------ |
| `X-Content-Type-Options: nosniff`                  | Content-Type の推測の禁止                                    |
| `X-Frame-Options: DENY`                            | 他サイトの iframe への埋め込みの禁止（クリックジャッキング） |
| `Referrer-Policy: strict-origin-when-cross-origin` | 他サイトへ送る Referer の絞り込み                            |
| `Permissions-Policy`                               | カメラ・マイク・位置情報・決済の無効化                       |
| `Cross-Origin-Opener-Policy: same-origin`          | 他ウィンドウとの参照の切り離し                               |
| `Strict-Transport-Security`                        | HTTPS の強制（HTTPS でない環境では無視される）               |
| API に `Cache-Control: no-store`                   | 採点・進捗の応答を、キャッシュさせない                       |

**CSP（Content-Security-Policy）は、今は入れない。** テーマの初期化スクリプト（インライン）と、Next の内部スクリプトがあるため、安全に入れるには nonce の仕組み（リクエストごとに値を変える）が要る。nonce を使うと、**全ページが動的描画になり**、静的生成の利点が失われる。ハッシュ方式の可否も含めて、別の課題として扱う。

### 利用規約・プライバシーポリシー

`/terms`・`/privacy` を用意し、フッターからリンクする。**現状の事実だけを書く**（Cookie を使わない、進捗はブラウザ内、採点の回答は保存しない、ログイン機能はまだない）。ログイン機能を公開する前に、保存する情報・保存先・削除方法を、プライバシーポリシーに追記する（必須。文書にもそう書いてある）。最終更新日は `LEGAL_UPDATED` で管理する。

**これは法的助言ではない。** 公開前に、運営者が内容を確認すること（連絡先は、GitHub Issues にしている）。

### メタデータ・SEO

- `metadataBase` を、環境変数 `NEXT_PUBLIC_SITE_URL` から決める（未指定は localhost）。canonical・OGP・sitemap の絶対URLに使う
- `robots.txt`（API をクロールさせない）、`sitemap.xml`（レッスン25本。更新日は、公式で確認した日 `verifiedAt`）、SVG のアイコン
- **本番では `NEXT_PUBLIC_SITE_URL` を必ず設定する**。未設定だと、sitemap や canonical が localhost を指す

### サーバーレスでの API

Vercel などでは、実行に必要なファイルだけがバンドルされる。`/api` は、実行時にレッスン(MDX)とチートシート(YAML)を読むので、`outputFileTracingIncludes` で明示的に含める（ビルドの成果物で、25本とYAML 2つが含まれることを確認済み）。

### E2E とアクセシビリティ検査

- `e2e/` に、ワークスペースのパッケージとして置く（`site` / `learning` / `content` / `a11y`）。使い方は `e2e/README.md`
- 本番ビルドを、実ブラウザ（Playwright）で検査する。アクセシビリティは axe-core で、WCAG 2.x A/AA の違反が1件でもあれば失敗
- **CI では、まだ実行しない。** 分単位かかり、待ち時間のずれによる偶発的な失敗があり得るため。導入するなら、まず `site`（ブラウザ不要）を、必須でないワークフローとして加える（`e2e/README.md` に提案を書いた）
- 機械検査が「要確認」にしたもの（グラデーション上の文字など）は、**配色トークンから計算するテスト**（`design-tokens.test.ts`）で、最悪の位置でも基準を満たすことを確認する。ライト/ダークを2か所に書いているので、一致も検査する

## 検査で見つけて直したこと

- 検索ボタンの読み上げ名が、見えている文字とずれていた（WCAG 2.5.3）→ ショートカット表示を CSS の疑似要素にし、`aria-keyshortcuts` で支援技術に伝える
- モバイルの下部タブバーの文字が、半透明の背景のせいでコントラスト不足（WCAG 1.4.3）→ 不透明にした
- 用語集で、存在しない見出しを `aria-labelledby` が指していた（機械検査の「要確認」から発見）→ 見出しがあるときだけ関連づける
- ホームの見出しのグラデーションの終点が、最悪の位置で 3:1 に届かなかった → 終点の色を濃くした

## 結果

- 機械検査では、56条件（ページ × ライト/ダーク × デスクトップ/モバイル × 操作中の状態）で、違反 0 件
- **機械検査は、アクセシビリティの問題の一部しか見つけられない。** キーボードだけでの操作、スクリーンリーダーでの読み上げは、人が確認する必要がある（未実施）
- Lighthouse によるパフォーマンスの計測は、別途行う
- CSP が無いため、XSS への多層防御は、まだ弱い。公開前の課題として残る
