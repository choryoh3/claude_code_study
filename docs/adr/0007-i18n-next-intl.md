# 0007. 多言語対応の土台（next-intl・URLに言語を付けない）

- 日付: 2026-10-19
- 状態: 採用

## 背景

画面の文言がコンポーネントに直接書かれていた。将来の多言語化に備え、文言をリソースとして一元管理したい。公開URLは変えたくない。

## 決定

- **next-intl を使い、文言は `apps/web/messages/<locale>.json` に集約する**（現在は `ja` のみ）
- **URLには言語を付けない**（`/roadmap` のまま）。言語の決定は `src/i18n/request.ts` に集める
- **現在は言語を `ja` に固定している**。cookie や Accept-Language を読むと、全ページが動的描画になり、静的生成（SSG）の利点が失われるため。言語を増やすときは、ここで cookie 等から決める（その場合の描画方式の変更は、そのときのADRで扱う）
- **メッセージのキーを型で検査する**（`src/i18n/global.d.ts` の `AppConfig`）。存在しないキーや、ICUの引数の渡し漏れは、コンパイルエラーになる
- **文言の直書きをテストで禁止する**（`no-hardcoded-text.test.ts`）。構文木で文字列・テンプレート・JSXの文字だけを検査し、コメントは対象外。例外は、画面に出ない開発者向けエラーだけで、許可リストに理由を書く
- **辞書の整合性をテストする**（`messages.test.ts`）。言語ごとのキー構造・ICU引数・タグの一致、バッジ・レベルの定義との対応、空文字の禁止
- **見た目に関わる文言は、辞書側にタグで持たせる**。見出しの強調や折り返し位置（`<accent>` `<nowrap>`）、フッターのリンク（`<link>`）。語順が言語で変わっても、辞書だけで対応できる
- **日付などの書式は `useFormatter`（Intl）で整形する**。「2026年10月19日」のような形式を、コードに書かない
- **本文の見出しIDは、文言ではなく位置で対応させる**（ゴール→前提→…の固定順序）。見出しの文言は言語ごとに違うため、コードに日本語を置かない

## 対象外（今のところ日本語のまま）

- **レッスン本文・クイズ・チートシート・用語集**は、コンテンツ（データ）であり、辞書の対象ではない。多言語化するときは、言語ごとにコンテンツを持つ（例: `packages/content/lessons/<locale>/...`）。ない言語は日本語にフォールバックする方針を、そのときに決める
- **APIのエラーメッセージ**（`{ error: { code, message } }` の `message`）は日本語。画面側は `code`（や HTTP ステータス）から自分の辞書の文言を選ぶので、画面には影響しない
- **バッジの名前・説明**は、DBのseedと共有する定義（`packages/schemas`）が日本語。画面は辞書の文言を使い、日本語の内容が定義とずれないことをテストで保証している

## 言語を追加するときの手順

1. `src/i18n/config.ts` の `locales` に追加する
2. `messages/<locale>.json` を作る（`ja.json` とキー構造を同一にする。`messages.test.ts` が検査する）
3. `src/i18n/request.ts` で言語の決め方を実装する（描画方式の変更の影響を確認する）
4. コンテンツ（レッスン等）の扱いを決める

## 結果

- 画面の文言の変更は、辞書の1か所で済む。誤字や言い回しの修正で、コンポーネントを触らなくてよい
- 辞書のキーはコンパイル時に検査されるが、**使われていないキー**は検出しない（辞書が膨らんでいないかは、レビューで見る）
- すべての画面で `useTranslations` / `getTranslations` を使う必要がある。サーバーコンポーネントでは `getTranslations`（非同期）、同期のコンポーネントでは `useTranslations` が使える
